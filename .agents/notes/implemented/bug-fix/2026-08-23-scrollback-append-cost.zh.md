# Agent Note: Scrollback retention appends in O(chunk) instead of O(buffer)

Status: implemented

[English](2026-08-23-scrollback-append-cost.md) | 中文

## 问题

terminal-bash 的 scrollback 在每个 PTY 数据事件上用整段字符串操作来执行字节与行数上限：每次 append 都拼接保留值、按换行拆分、用 `Array.from` 为每个码点生成一个元素，再对尾部切片并重新拼接。无论是否有人读取，输出都会在整个会话生命周期内持续写入 scrollback；一旦缓冲达到默认 4 MiB 上限，每个新块都要对整个窗口做多次遍历并产生两个大型中间数组。因此单个模型发起的输出洪泛就会让事件循环陷入持续的二次方消耗，饿死同进程中的其他会话和插件。内存上限是正确的，只有 CPU 是病态的。

## 决策

`BoundedOutputBuffer`（packages/terminal/terminal-bash/src/scrollback.ts）现在以 UTF-8 字节形式把数据保存在一块 `maxBytes + 3` 字节的固定环形缓冲中，而不是 JS 字符串。每次 append 只编码传入的数据块、扫描其中的换行符并写入环内；当数据块超过剩余空间时释放最旧的字节，这一过程绝不会丢失上限本应保留的数据。字节上限先释放头部 `size − maxBytes` 字节，再把切割点推进到下一个 UTF-8 首字节，与原先"保留不超过 `maxBytes` 字节的最长完整码点尾部"的规则完全一致；三个字节的冗余保证该切割位置总在已保留数据之内。可选的行数上限增量地记录换行偏移，释放头部数据直到暴露出最后 `maxLines` 个分段；偏移按流位置寻址，因此更早的字节裁剪不会改变行上限所指向的分段，索引在多数条目落后于窗口时定期压缩。长度超过环的数据块会让窗口替换为该数据块自身被截断后的尾部，这里可证明包含合并后流所能保留的全部字节。解码只发生在 `snapshot()` 与 `consume()` 中；就绪轮询改读新的 `truncated`/`empty` 取值器，轮询不再触发窗口解码。

输出一致性成立的原因是：旧算法每次 append 执行"保留最后 `maxLines` 个分段，然后保留 `maxBytes` 字节内最长完整码点尾部"，它组合到整条流上与本实现维护的后缀相同——两个上限都只释放头部数据，切割位置单调前移，而行上限可能指向、却被更早的字节裁剪移除的前缀必然位于窗口起点之后。数据块以完整解码文本到达，因此环总是起始于码点边界，UTF-8 解码可以复现原先字符串域的值。

## Alternatives considered

**保留解码后的分块队列并在读取时拼接。** append 仍是 O(chunk)，但窗口以分块与拼接结果两份形态驻留内存，且字节裁剪仍需跨分块边界做字节记账。单一环形缓冲删除了边界处理。

**只按行数或只按字节数设置上限。** 两个上限都是当前工具消费者的契约（`read` 分页按行限制，`maxReadBytes` 按字节限制）；去掉任何一个都会改变返回输出。

**对 PTY 事件限流或合并。** 采样只是隐藏放大效应而保留其成因，并且会丢弃当前契约承诺交付的输出。

**引入终端模拟库负责保留。** 本包刻意渲染规范化的面向行的文本；模拟库带来的处理与依赖重量没有任何当前消费者使用。

## Consequences

append 的成本与传入数据块成正比，包含上限执行与头部释放；`snapshot()`、`consume()` 和 `read()` 因按需解码仍是 O(window)。环形缓冲增加三字节冗余，换行索引通过周期性压缩保持有界。上限、截断标志与 UTF-8 边界行为保持不变，由针对旧实现的随机化 oracle 测试、精确的多字节与行上限用例，以及断言饱和的 512 KiB 窗口上 20,000 次 append 远低于二次方成本的稳态护栏测试锁定。
