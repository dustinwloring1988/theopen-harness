# Agent Note: 在 toh-lsp-stdio 中为未应答的 server→client 请求设置并发上限

Status: implemented

[English](2026-08-23-lsp-server-request-reply-bound.md) | 中文

## 问题

`toh-lsp-stdio` 对基础协议的每个入站方向都设有上限——帧解码器限制头部与消息体大小，stderr 是有界尾部——但出站的应答路径没有任何上限。每条入站的 server→client 请求都会生成一个处理器，把应答帧写入子进程的 stdin，而当管道写满时，Node 对 `Writable` 写入的缓冲是无上限的。一个恶意或损坏的服务器只要以快于应答排空的速度发出未应答请求，就能通过滞留的应答写入让宿主内存无界增长，完全绕开本包针对同一威胁（"恶意或损坏的服务器不能耗尽内存"）设置的所有限制。这种失败是无声的：缓冲持续增长期间不会有任何错误浮现。

## 决策

`LspConnection` 统计应答写入尚未落定的 server→client 请求数量，超过固定上限 32（`MAX_IN_FLIGHT_SERVER_REQUESTS`）后拒绝新的请求。超限会走既有的致命失败路径——保留原因 `language server exceeded 32 unanswered server-to-client requests`，拒绝所有待完成的 client 请求，终止进程树——与帧错误的治疗方式一致。由于保留原因就是该连接的传输失败标识，provider 既有的所有权安全恢复逻辑无需改动即可生效：被污染的实例被处置，该查询在新进程上透明地重试一次。

该上限是固定常量而非配置项：它是高于任何合法流量的安全不变量（真实服务器的并发只有个位数——进度创建、configuration 拉取、能力注册），且按工作区串行的查询使普通并发保持在一。

## 考虑过的替代方案

**在 `stdin.writableNeedDrain` 置位时暂停 stdout 处理。** 否决：只要有写入在进行，drain 就会短暂置位（一份大的 `didOpen` 文档经常填满管道），因此读暂停需要自己的存活时限，并与致命错误路径交织，相比统计处理器数量收益甚微。

**对超出上限的请求丢弃应答或回复错误。** 否决：丢弃应答会让等待 `workspace/configuration` 的合规服务器停滞，而错误应答本身仍是一次缓冲写入——什么都没有限制住。

**把上限做成每个服务器条目的配置。** 否决于仓库规则：协议常量与安全不变量保持固定；也没有消费方证据表明需要超过个位数的并发服务器请求。

## 后果

- 未应答 server→client 请求造成的内存滞留现在被限制在上限之内（几十个小帧），而不是无上限。
- 合法地超过 32 个并发未应答请求的服务器会被终止而非继续服务；没有观察到这样的服务器，且可诊断的退出原因会写明该上限。这是为保持内存保证绝对成立而接受的取舍。
- 计数器在应答写入落定时无论成败都会递减，因此缓慢（而非停滞）的排空不会触发上限。
