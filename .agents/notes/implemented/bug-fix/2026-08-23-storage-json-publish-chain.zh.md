# Agent Note: storage-json serializes overlapping publishes on an in-unit chain

Status: implemented

[English](2026-08-23-storage-json-publish-chain.md) | 中文

## 问题

JSON KV 的每个写入原语都会同步修改权威的内存映射，然后重新发布整个文件。每次发布都把当前状态序列化进一个全新的临时文件，并独立地 `rename()` 覆盖目标，因此两个重叠的未等待写入会产生两个相互独立的快照去竞争同一个重命名目的地：谁的重命名最后落盘谁胜出，而那可能是过期的快照。一条 `putRecord` 已经成功返回的记录可能从磁盘上无声消失，并在重启后仍然缺失——这是完成顺序者胜，而 `atomic.ts` 却断言的是 last-write-wins。

领域层的每单元写入链（[领域 KV 存储](../../proposed/architecture/2026-07-24-domain-kv-storage-and-workspace.zh.md)）保证领域操作串行，所以经由该路径的竞态窗口很窄，但存储契约明确允许直接使用 `backend.kv.open(...)` 的消费方，它们正会踩中。`close()` 只排空在途写入、不做修复性发布，分歧因此能活过一次正常关闭。

## 决策

每个单元现在拥有自己的发布链：一条已定格的 promise 尾巴，每次发布追加到链尾，而每个链节在自己的时隙运行时才读取完整内存状态，而不是在写入发起时读取。整文件替换按调用顺序逐个落盘，最后一次重命名永远携带最新状态；一旦某次写解析完成，介质上就持有它之前发出的全部已确认写入。被拒绝的链节只在尾巴上吞掉——发起调用的调用方仍然恰好观察到一次自己的错误，内存照旧回滚，而下一个排队中的时隙要等该回滚执行完才会序列化。`close()` 等待同一条尾巴，因此关闭会排空被挂起和尚未开跑的发布；排空之后介质与内存一致，因为最后一个落盘的时隙写入的是完整状态，任何失败的发布都在其后继者运行前完成了回滚。共享的 `KvUnit` 契约现在陈述这条"持久性抗重叠"保证，而不是否认单元内串行；每次调用写什么仍由调用方负责（提案后端契约的第 4 条相应收窄——持久性排序移入单元内，调用方拥有的逻辑排序保留）。

## 测试

JSON backend 套件 mock 了本包的 atomic-write 模块：一个直通真实实现的 seam，可在下一次替换上布设一次性挂起。两个测试都把第一次发布停在半路，再发起第二个重叠的未等待 `putRecord`，并钉住链条行为：第二次调用发出后文件必须仍不存在——旧的独立快照发布在那一点上第二条重命名已经落盘——释放挂起后，最终文件与重新打开的介质都必须包含两条记录；其中第二个测试在两条写入都在排队时关闭单元，断言排空后两条记录都在磁盘上。把 `publish()` 还原为逐调用独立替换时，套件会确定性地复现丢数据。

## 备选方案

**给重命名加版本守卫。** 给每个快照盖单调递增的版本号，让输家检测到自己覆盖了更新的文件并补一次发布。已否决：它让并发整文件替换继续竞争，还要增加一条修复路径，其交错情况比直接给重命名排序更难钉住；串行化是删除竞态，而不是裁决竞态。

**维持"调用方负责排序"作为全部答案。** 已否决：对获准的直接 KV 消费方而言，没有任何结构性机制阻止重叠调用，这等于把一个无声的数据丢失窗口留在文档注意事项背后——正是本次报告的 bug。

## 影响

重叠的直接 KV 写入不再可能丢弃一条已确认的记录。发布现在严格一次只跑一个替换，放弃了重叠调用间并发准备临时文件的吞吐——实际无感，因为领域层的每单元链早已把它们串行化。每个调用方的"失败即回滚"语义不变。跨进程写入方仍然互不同步（整文件 last-writer-wins）；README 的已知限制条目依旧如此声明。
