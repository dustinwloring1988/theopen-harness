# Agent Note: storage-json 在单元级链上串行化重叠发布

Status: implemented

[English](2026-08-23-storage-json-publish-chain.md) | 中文

## Problem

JSON 存储单元的每个写入原语都会同步修改内存，并立即通过独立的「临时文件写 + 重命名」序列暂存自己的整文件快照（`packages/storage/storage-json/src/unit.ts`）。两个重叠且未等待的调用因此会用两个重命名竞写同一路径，最后落盘的重命名胜出——它可能携带旧快照。一条已成功解析的记录可能在重载后从磁盘上无声消失；`close()` 只排空在途写入，不修复这种分叉。经由 `storage-domain` 的触达面较窄，因为它的按域链串行化写入（[领域 KV 存储设计](../../proposed/architecture/2026-07-24-domain-kv-storage-and-workspace.zh.md)），但 KV 契约允许直接使用 `backend.kv.open()` 的消费方，它们会踩中此问题。

## Decision

单元把每次发布链接到一条内部 promise 尾部之上，并在槽位运行时对状态做快照，因此最终重命名总是携带最新已确认的状态。失败发布的回滚在其失败的槽位内执行，所以下一个槽位的快照绝不会包含被拒绝的变更。`close()` 改为排空链尾，而不是逐个跟踪在途写入。公开的 `KvUnit` API 保持不变；共享契约文本现在允许单元串行化重叠发布，而跨调用的顺序仍由调用方负责。

## Alternatives considered

**重命名前做版本/代数检查。** 不采用：这需要原子比较交换的发布原语，Windows 的 `MoveFileExW` 替换式重命名并不提供，而重试循环会重新引入它们想防住的交错。

**把串行化完全留给调用方。** 不采用：单元此前确实把排序交给调用方，但该故障模式对被允许的直接消费方是无声数据丢失，而修复只花一条 promise 链且不改 API。

**入队时快照而非槽位运行时快照。** 不采用：在有链的前提下正确但浪费——每次重叠都重复发布早已过时的快照；槽位运行时快照让每个排队写入都携带当前状态。

## Consequences

- 同一单元的并发写入者一次只进行一个发布；吞吐与整文件模型的单写者立场一致，而不是竞跑多个独立临时文件。
- 失败的发布不再可能把已回滚的变更泄漏进下一次成功的发布。
- 回归覆盖驱动重叠且未等待的 `putRecord` 调用，断言介质最终是最新载荷且两条兄弟记录俱在，同时保留顺序写入覆盖。

## Testing

`pnpm run test --filter @buckeyestudio/toh-storage-json` 覆盖重叠发布回归与共享 KV 后端契约套件。
