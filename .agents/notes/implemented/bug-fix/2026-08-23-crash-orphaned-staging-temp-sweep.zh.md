# Agent Note: 后端打开时清扫崩溃遗留的暂存临时文件

Status: implemented

[English](2026-08-23-crash-orphaned-staging-temp-sweep.md) | 中文

## 问题

三个持久化层面都只在成功路径或捕获错误后清理自己的暂存临时文件：JSONL 会话后端在链接或无覆盖重命名之前，把 `session.jsonl[.zstd].<random>.tmp` 写在最终日志旁；本地附件存储把暂存对象硬链接出 `attachments/v1/tmp/<uuid>`，之后再 unlink 暂存副本；请求版本缓存用 `<hash>.<uuid>.tmp` 重命名覆盖其缓存条目。在临时写入与发布之间发生崩溃或断电，文件就会永久滞留。仓库中从来没有任何清扫逻辑处理这些名称，残留只能靠手动删除；而发现机制只读取目录和固定的工件名，这些散落文件同样不可见。

## 决策

每个后端挂载时通过类插件的 `[Service.init]` 生命周期钩子执行一次尽力而为的清扫。JSONL 后端删除根目录下每个会话目录内的所有 `*.tmp` 文件。附件存储一次遍历清理它的两个层面：私有 `tmp/` 暂存目录中修改时间早于本进程启动的条目，以及请求版本缓存对象旁的所有 `*.tmp` 文件。

垃圾判定依据因层面而异，清扫也据此执行。已发布的日志或缓存请求版本的名称永远不含 `.tmp`，因此任何 `*.tmp` 邻居无论多新都是可证明的残留——删除它绝不会影响已发布工件。附件 `tmp/` 下的暂存条目以 UUID 命名，无法凭名称区分是否正在写入，因此以时间为判据：挂载时本进程尚未创建任何文件，而在本进程启动之后创建的并发写入者文件保有新鲜 mtime，从而受到保护。清扫只触碰普通文件和符号链接叶子（按链接本身删除，绝不跟随），跳过目录，不碰非匹配名称。

清扫失败绝不导致 open() 失败：枚举错误和单文件删除失败连同清扫数量一起以 debug 记录，因为残留无害——没有读取路径会触达那些名称——而被锁定的文件不应让会话或附件操作卡在一个无法修复的挂载错误后面。每次启动都会重试上次幸存的文件。

## 已考虑的替代方案

**无条件删除 `tmp/` 条目。** 否决：并发进程正在写入的暂存文件会在写入与链接之间消失，使一次本来健康的发布失败。mtime 保护把收集范围限定在明显早于本进程的文件。

**对 `*.tmp` 邻居施加同样的 mtime 保护。** 否决：在名称已经证明是垃圾的地方，年龄毫无增益，反而会让启动窗口内重启的新写入者留下的旧孤儿继续存活——这正是清扫要阻止的累积。（保护仍保留给 `tmp/`，那里的名称证明不了任何事。）

**周期性后台清扫器或共享工具包。** 否决：残留按存储根目录累积，因此在拥有它的后端打开时清扫一次，把工作限定为每次挂载一次小型目录遍历，无需定时器、跨包依赖边或后端间协调。

## 验证

两个包的测试在真实的已发布 JSONL 日志旁和准备好的附件根内植入孤儿临时文件，然后断言过期与新鲜的 `.tmp` 文件消失，而日志、已存储对象、缓存变体、非匹配文件和范围外位置逐字节保留。其他测试覆盖公开打开路径上的 mtime 保护（未来时间戳的暂存条目幸存）、单条目失败隔离（一个被锁文件不掩盖其余条目）、枚举失败向调用方传播，以及清扫拒绝时挂载仍然成功。两个包的既有套件全部不变通过。

## 后果

崩溃遗留的暂存文件由拥有它的后端在下次挂载时收集，而不是无限累积。并发写入者的临时文件若在本进程启动前创建、发布途中被删（仅 `*.tmp` 邻居可能），会丢失一个 append 批次并通过协调器的保留缓冲路径重试；已提交数据不受影响。清扫在每次挂载时运行，包括短命进程，成本是两级目录 `readdir` 加每个候选一次 `lstat`。
