# Agent Note: The JSON-RPC line transport caps an unterminated frame and fails the peer past it

Status: implemented

[English](2026-08-23-jsonrpc-line-transport-frame-cap.md) | 中文

## Problem

`JsonRpcLineTransport` 在出现 `\n` 之前把所有入站字节保留在一个字符串缓冲里，既不限制等待时长，也不限制累积大小。一个不换行持续发送字节的对端——有缺陷的客户端、损坏的流、恶意进程——会让传输层缓冲在两个线端（SDK 客户端 ↔ 经 stdio 的运行时子进程）无限增长，直到运行时进程内存耗尽。该失败模式是静默的：请求保持挂起，没有任何错误浮出，而内存持续攀升。

## Decision

传输层现在接受可选的 `maxFrameBytes`（`JsonRpcLineTransportOptions`），默认 `DEFAULT_MAX_FRAME_BYTES` = 16 MiB，并在构造时校验为正的安全整数。上限按跨块边界的 UTF-8 字节数计量：传输层在解码字符串之外同步跟踪未排空输入的字节长度，因此跨 `Buffer` 块拆分的多字节字符无法逃过计量。

当输入在无换行挂起的情况下超过上限时，传输层丢弃已缓冲的帧，以携带 `-32700`（解析错误）错误码的 `JsonRpcResponseError` 销毁调用方的输入流，并经既有的 `onInputError` 路径让流错误拒绝所有挂起请求。销毁输入在流层阻止后续投递；连接不可能从帧中间恢复，所以正确的响应是拆除而不是重新同步。之后的块一律不再保留。该上限只约束单个未完成帧：等待分发的完整行总量可以合法地超过它，先排空它们使批量发送依然有效。

16 MiB 远高于今天任何合法的 SDK 帧（会话事件、提示、工具载荷），同时解码后的保留量不超过配置值，因为 UTF-8 字节数不会以超过一比一的比例多于其 UTF-16 码元。

## Alternatives considered

**固定的内部常量，不提供选项。** 否决，因为两个生产消费者处于不同的信任边界——服务器读取本地 stdio，客户端读取自己派生的子进程，`subagent-codex` 又接线另一个对端——所以明知帧很小的部署应当能收紧上限而不必分叉这个类。仓库约定把固定协议常量留给外部规范；这道天花板是资源策略，不是线规则。

**丢弃字节直到下一个换行来重新同步，而不是销毁流。** 否决，因为为寻找下一个 `\n` 扫描无界的敌意输入会重新引入本要防止的增长，且已消费进被丢弃帧的字节会让对端的请求/响应 id 流变得含糊。交付过超大帧的连接是故障的；让它响亮地失败胜过静默跳过不可知数量的流量。

**只失败挂起请求但保持流挂接，并丢弃后续的超大块。** 否决，因为已分离但仍活跃的输入会继续向一个已宣布连接不可用的传输层投递数据，让两端对线路是否可用各执一词。

## Consequences

- 对端再也无法通过无换行的流式发送增长运行时进程的内存；每个方向的保留量由构造即有界。
- 触及上限的 SDK 会话看到未完成的 `request()` Promise 以 `JsonRpcResponseError` 错误码 `-32700` 被拒绝，子进程 stdout 被销毁——与其他任何流死亡相同的关闭表面，因此客户端经既有的退出处理恢复，而不是走新路径。
- 大于 16 MiB 的合法单帧现在会失败而不是缓慢成功；需要更大帧的消费者在构造时调高 `maxFrameBytes`，当前没有消费者需要这样做。
- 字节计量增加一个数字状态和每排空一行一次减法；分块的多字节记账保持精确，无需重新扫描缓冲。

## Testing

`packages/sdk/protocol/tests/transport.spec.ts` 钉住默认值、在构造时拒绝非法选项、证明超大无换行流以 `-32700` 拒绝挂起请求且不再保留后续输入、证明超过上限的完整行仍会分发、演练恰好在上限处的边界（上限处允许缓冲，严格超出才溢出），并以 5 字节上限下的多字节帧钉住按字节计量的语义。
