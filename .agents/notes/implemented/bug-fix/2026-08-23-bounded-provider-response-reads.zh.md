# Agent Note: Bound every provider response body the host buffers

Status: implemented

[English](2026-08-23-bounded-provider-response-reads.md) | 中文

## 问题

三个 web 搜索提供方都用无上界的 `response.json()` 解析上游响应，DeepSeek chat 适配器也用无上界的 `response.text()` 读取非 2xx 响应体。两者都会在任何检查执行之前，把完整响应体缓冲进宿主内存。这些端点可由部署方和用户配置（`baseURL` 是设置字段，部分由环境变量解析），因此一个返回多吉字节响应体的恶意或被攻陷端点就能耗尽进程内存。仓库已有规则把用户输入的端点视为必须施加流式上限——`llm-pi-ai` 的发现流程拒绝超过 4 MiB 的模型列表，`web-fetch-http` 以 5 MiB 封顶页面读取——但这四处调用点先于该规则存在或被遗漏。

## 决定

宿主缓冲的每个 HTTP 响应体现在都经由包内私有的两阶段有界读取器读取：声明的 `Content-Length` 超过上限时取消未读的响应体并立即拒绝；否则流式累计，一旦总字节数越过上限即拒绝。四个位置的统一上限是 4 MiB（各搜索提供方的 `MAX_RESPONSE_BYTES`、chat 适配器的 `MAX_ERROR_BODY_BYTES`），与发现流程针对 JSON 元数据载荷和错误体所设的先例一致；适配器的成功调用仍通过 `parseSse` 流式处理 SSE，从不缓冲。溢出时抛出调用方自身的错误类型，消息中写明提供方与上限——搜索响应用 `WebError` `WEB_PROVIDER_ERROR`，适配器错误体用按状态映射的 `LlmError` code——让超大响应大声失败，而不是被包装成"无法解析的响应"诊断。错误路径的消息富化保留既有规则：只有可用的响应体才能改进状态行消息，但超限拒绝现在会冲出该回退路径，不再被它掩盖。

每个包拥有自己的私有读取器，与本已本地化的 abort 与整数谓词并列，并以 `jscpd` 忽略区间标记。仓库不存在共享的 HTTP 传输内部工具包；为一个函数新造一个会违背 seam 包"内部实现保持本地"的明确约定，徒增跨组公共 API 面。

## 考虑过的替代方案

**新建 util 包共享同一个读取器。** 否决：仓库既定模式就是包内私有实现（discovery、fetch-http 的截断式读取器、agent-instructions 的文件读取器各有本地差异），搜索提供方甚至刻意不把两行的谓词放进公共 seam，而新包会让四个独立插件为一个函数耦合到新的 workspace 依赖。

**对超限响应体截断而非拒绝。** 在这些调用点否决：被截断的 JSON 文档无法解析，截断只会把清晰的拒绝变成误导性的"响应不可处理"，同时仍要付出大部分传输成本；`web-fetch-http` 可以截断，是因为它返回给消费方的散文页面能容忍残缺内容。

**只给成功响应体设上限。** 否决：错误路径是更低成本的攻击面——恶意端点可以在任意非 2xx 状态下返回巨大响应体，旧代码同样会照单全收地缓冲。

## 验证

每个搜索提供方的 spec 覆盖：恰好等于上限的成功响应正常解析；成功与错误两条路径上越过上限的流式响应均被拒绝且断言确切的拒绝消息；声明长度超限的拒绝被证明不会排空响应体（fixture 流永不关闭）；有界读取期间的中止以 `WEB_ABORTED` 呈现。适配器 spec 通过真实的 mock HTTP 服务器覆盖流式超大错误体与声明长度超限两种情况。既有测试套件固定了正常、畸形与中止路径的不变行为。

## 后果

配置的端点再也无法通过任何被缓冲的响应读取耗尽宿主内存；每次调用的最坏情形是 4 MiB 上限加上分片拼装。超过上限的合法端点现在会使其调用失败而非成功——格式良好的上述载荷都不太可能达到 4 MiB。四个读取器按设计彼此重复；未来若落地传输层统一的 HTTP 服务（适配器中的 `TODO(http)`），那里才是合并它们的位置。
